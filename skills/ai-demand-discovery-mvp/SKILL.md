# AI 需求挖掘与 MVP 边界

## 使用场景

当用户给出一个模糊业务痛点、业务方需求、AI 产品想法或面试问题时，使用本 Skill 判断：

- 这个需求是否适合 AI 解决
- 哪些是真需求，哪些是假需求或越界需求
- MVP 阶段做什么、不做什么
- 后续版本如何规划

## 核心原则

不要直接接功能点。先判断业务问题，再判断 AI 适配性。

万能链路：

```text
业务目标 -> 用户任务 -> 原始流程 -> 痛点节点 -> AI 可切入点 -> 需求池 -> 需求分类 -> 优先级 -> MVP 边界
```

## 需求分类

| 类型 | 定义 | 处理方式 |
| --- | --- | --- |
| 真需求 | 有真实场景、用户任务明确、数据可支撑、风险可控、能验证效果 | 进入需求池并排序 |
| 合规越界需求 | 用户可能高频提，但存在合规、伦理或安全风险 | 拒答、风险提示或人工流程 |
| 能力越界需求 | 当前模型、数据或工具能力无法稳定支撑 | 暂缓，作为探索项 |
| 阶段越界需求 | 有价值但成本高、依赖多，不适合 MVP | 放入后续版本 |
| 伪需求 | 没有真实场景或业务价值，只是听起来像 AI 功能 | 不做 |

## 判断维度

1. 业务价值：是否服务增长、效率、转化、留存、成本或风险控制。
2. 用户频次：是否高频，或虽然低频但高价值。
3. 痛点强度：用户当前是否真的痛，是否有替代方案。
4. 数据来源：是否有稳定数据，是否可追溯。
5. AI 适配性：AI 是否适合处理该任务，是否比规则/人工更优。
6. 成本 ROI：开发、数据、模型、运营成本是否值得。
7. 风险边界：是否有合规、安全、误导、隐私等风险。
8. 可评测性：是否能定义指标判断做得好不好。

## 工作流

1. 复述业务目标  
   用一句话说明业务方真正想解决什么，不复述功能名。

2. 还原原始流程  
   描述没有 AI 时，用户如何完成这件事。

3. 找痛点节点  
   标出每一步的耗时、难点、错误风险、信任问题。

4. 生成需求池  
   把痛点翻译成需求，不急着排序。

5. 分类需求  
   将需求分为真需求、合规越界、能力越界、阶段越界、伪需求。

6. 设定优先级  
   按业务价值、用户频次、数据成熟度、实现成本、风险、前置依赖排序。

7. 定义 MVP  
   明确 V1 做什么、不做什么、为什么。

8. 定义指标  
   给 MVP 配套成功指标和风险指标。

## 示例口径

“我不会拿到业务方说要一个 AI 助手就直接开始设计功能，而是先还原用户没有 AI 时怎么完成任务，再看每个节点的痛点、数据支撑、风险和可评测性。最后把需求分成真需求、合规越界需求和阶段越界需求，再确定 MVP 边界。”
