# Multi-Agent 产品链路设计

## 使用场景

当一个 AI 产品不能靠单次大模型回答解决，需要多个任务、多个工具或多个数据源协作时使用。

## 核心判断

不是所有 AI 产品都需要 Multi-Agent。只有当存在以下情况时才考虑：

- 用户问题经常是多意图
- 不同任务依赖不同数据源
- 不同节点输出要求不同
- 单一 Workflow 过于僵硬
- 需要中间结果影响后续路径
- 需要可观测、可评测、可兜底

## 基础架构

```text
用户 Query
-> Planner：业务边界判断、意图识别、子问句拆解、路径选择
-> 子 Agent：按任务调用工具和数据
-> Shared Context：沉淀工具返回结果和关键依据
-> Summary：基于依据输出结构化结果
```

## 工作流

1. 定义用户问题类型  
   列出典型 Query、OOD、多意图 Query、模糊 Query。

2. 收敛任务范式  
   不要按表面关键词拆 Agent，要按任务和执行路径拆。

3. 设计 Agent 分工  
   每个 Agent 只负责一类清晰任务。

4. 定义 Planner 能力  
   包括业务边界、意图识别、槽位提取、子问句拆解、路径选择。

5. 设计执行路径  
   明确单 Agent、串行、多 Agent 组合、并发、兜底路径。

6. 定义节点输入输出  
   用结构化字段描述每个节点输入、输出、状态和错误信息。

7. 设计异常兜底  
   包括召回为空、依据不足、多意图冲突、越界问题、工具失败。

8. 设计评测指标  
   路由、槽位、召回、依据、结构、响应时间。

## 常见路径

```text
只调用单 Agent
先 A 后 B
A 和 B 并发后汇总
A 输出作为 B 的上下文
A 失败后降级到 B 或直接兜底
```

## 质量标准

一个好的 Agent 链路必须能回答：

- 用户问题进来后先判断什么？
- 为什么调用这个 Agent 而不是那个？
- 每个节点拿什么数据？
- 中间结果为空怎么办？
- 最后结果凭什么可信？
- 出现 Badcase 怎么定位？
