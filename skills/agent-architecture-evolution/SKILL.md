# Agent 架构演进诊断

## 使用场景

当需要回答或判断：

- 为什么从 Workflow 升级到 Plan
- 为什么引入 ReAct
- 当前 Agent 链路是否过度设计
- 多意图、多工具、多数据源如何编排
- 准确率和响应时间如何取舍

使用本 Skill。

## 架构选择

| 架构 | 适合场景 | 优点 | 问题 |
| --- | --- | --- | --- |
| 普通 RAG | 单一问答、固定知识库 | 简单、成本低 | 难处理复杂任务 |
| Workflow | 流程稳定、步骤固定 | 可控、易验收 | 对多意图和动态任务不灵活 |
| Planner | 需要任务拆解和路径选择 | 能处理复杂 Query | 执行中不一定动态调整 |
| ReAct | 需要根据工具结果边思考边行动 | 灵活、能动态调整 | 成本高、响应慢、过程难控 |
| Plan + ReAct | 既要规划又要局部动态调整 | 兼顾可控和灵活 | 设计和评测更复杂 |

## 诊断问题

1. 用户 Query 是否经常多意图？
2. 任务路径是否固定？
3. 中间结果是否影响下一步？
4. 工具调用是否可能失败或返回空？
5. 是否要求输出严格可控？
6. 响应时间能否接受变长？
7. 是否能评测每个节点？

## 工作流

1. 描述当前架构  
   当前是 RAG、Workflow、Plan、ReAct 还是混合。

2. 列出现实 Badcase  
   用真实问题说明当前架构的不足。

3. 判断根因  
   是 Prompt 问题，还是架构天然不适合。

4. 选择升级方向  
   不追新，按业务需要选择。

5. 说明取舍  
   准确率、响应时间、成本、可控性、可评测性。

6. 定义验证指标  
   路由准确率、依据一致性、任务完成率、响应时间等。

## 面试故事模板

```text
一开始使用 Workflow，因为单任务稳定、输出可控。
灰测后发现真实用户经常一句话里包含多个意图，Workflow 固定链路处理不好。
最初以为是 Prompt 问题，反复优化后发现是架构问题。
引入 Planner 后，系统能先拆 Query 再选择路径。
但 Plan 执行中不能动态调整，召回为空时仍可能继续生成完整但无依据的答案。
所以在执行层引入 ReAct，让子 Agent 根据工具结果动态调整或兜底。
最终牺牲一定响应时间，换来更高准确率和可信度。
```

## 注意

不要把架构升级讲成追热点。要讲成被真实 Badcase 和业务复杂度推动的产品决策。
