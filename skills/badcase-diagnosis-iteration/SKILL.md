# Badcase 归因与迭代

## 使用场景

当 AI 产品出现以下问题时使用：

- 回答看似完整但没有依据
- 用户点踩但原因不明显
- 多 Agent 链路变长后问题难定位
- 改了 Prompt 仍然不稳定
- 召回、路由、输出结构互相影响
- 线上问题需要沉淀到评测集

## 核心原则

不要一上来就调 Prompt。先定位问题节点。

```text
Badcase -> 复现 -> 拆链路 -> 对比预期 -> 标注标签 -> 定位节点 -> 优化动作 -> 回归验证
```

## Badcase 标签

| 标签 | 说明 |
| --- | --- |
| 路由错误 | 走错 Agent 或执行路径 |
| 槽位错误 | 时间、主体、维度、约束抽错或漏抽 |
| 子问句拆解错误 | 多意图没有拆清楚，或拆得过细/过粗 |
| 召回错误 | 找到的材料不相关 |
| 召回不足 | 材料太少，不足以支撑输出 |
| 依据不一致 | 输出结论没有被材料支撑 |
| 结构不稳定 | 输出格式、字段、顺序不符合要求 |
| 合规风险 | 越界表达、敏感建议、风险提示不足 |
| 时效风险 | 使用过期数据或时间范围错误 |
| 表达问题 | 太泛、太长、结论不前置、用户看不懂 |

## 归因流程

1. 记录原始 Query 和用户反馈。
2. 复现完整链路，保留中间日志。
3. 对比预期路由和实际路由。
4. 对比预期槽位和实际槽位。
5. 检查召回材料是否正确、充足、可用。
6. 检查输出结论是否被依据支撑。
7. 检查输出结构和业务表达。
8. 打 Badcase 标签。
9. 确定优化动作。
10. 放入评测集做回归。

## 优化动作映射

| 问题节点 | 优化方式 |
| --- | --- |
| Planner | 补充意图规则、反例 Query、槽位字段、路由约束 |
| 检索召回 | 调整关键词、时间范围、Top-K、Rerank、索引字段 |
| 数据源 | 补字段、补来源、清洗数据、增加权限/时效校验 |
| 子 Agent | 调整工具调用顺序、输入输出字段、失败重试 |
| Summary | 结论前置、绑定来源 ID、限制自由发挥、结构化输出 |
| 合规 | 增加拒答规则、风险提示、人工复审 |

## 输出模板

```markdown
## Badcase 原始问题

## 用户反馈

## 预期链路

## 实际链路

## 问题标签

## 根因判断

## 优化动作

## 回归验证
```

## 面试口径

“中后期 Agent 链路变长后，回答不好不一定是某一个节点的问题。我会把 Badcase 拆成路由、槽位、召回、依据、结构等标签，通过实际结果和预期结果对比，先定位节点，再决定优化 Prompt、规则、检索还是输出结构。”
